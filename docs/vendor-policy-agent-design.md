# 厂家政策监测 Agent：产品方案与技术实现方案

> 状态：阶段 0–4 的代码基础已实现；真实厂家样本、来源补齐和人工标注
> 仍需运营试运行验证；方案以 2026-11-28
> 项目现状为基线。
>
> 相关现状：[中心服务部署与采集现状](./center-status-2026-11-28.md)。
> 网关与账本位于 Facet 仓库；采集器、中心服务和后台位于独立的
> `facet-center` 仓库。下文路径均注明所属仓库。

## 1. 目标与边界

持续跟踪厂家免费额度、优惠活动、价格、使用限制和模型可用性等政策。
Agent 发现疑似变化后，应能自行判断现有证据是否足够、还缺什么、是否值得继续
调查，并在预算内选择下一步。调查结果与项目中**人工确认的账本**比较，再按影响
程度处理。

已确定的产品边界：

1. 小变化自动留痕；有业务影响的变化生成草稿。重大或不确定事项优先提示。
2. Agent 可以自主调查和生成草稿，但**不得直接修改正式账本、签名或发布**。
3. 人工确认是修改正式账本的必要条件；确认草稿不等于已发布。
4. 抓取失败、搜索无结果或页面内容消失，不足以单独证明政策取消。
5. 不保证发现所有厂家变化；来源覆盖、未覆盖范围和失败情况必须可见。

## 2. 当前基础与缺口

已具备：

- Facet 的 [`ledger`](../ledger) 保存厂家、活动、变更记录和来源；
  [`schema.json`](../ledger/schema.json) 定义正式账本契约。
- `facet-center/tools/collect/daily.py` 调度九个采集环节；
  `agent.py` 能解读页面并检查部分原文引用，但不是自主调查循环。
- `facet-center/center/db.py` 和 `center/app.py` 有投稿待审队列；
  Facet 的 [`render.py`](../tools/ledger/render.py) 和签名流程负责生成发布产物。

需先解决的实际缺口：

- 快照环节读取 `sources.json` 的 `vendors`，现有来源文件实际使用
  `probe_endpoints`；快照保存目录与 Agent 读取目录也不一致。
- 环节级成功不代表厂家级成功；页面全部失败仍可能显示成功，日报和退出状态
  不能充分反映采集质量。
- 每厂家当前只取一个公告页面；规则候选历史命中会跳过后续 Agent 解读，
  多源交叉验证与分流状态落盘不完整。
- 来源页面、账户额度和模型目录不是同一概念；当前额度环节默认解析公告页数字，
  不应将其等同于真实账户余额。
- 现有投稿队列只有 `verified/rejected` 等简单状态，不会自动修改账本，
  也不足以记录完整调查与审核历史。
- 当前 `evaluate.py` 将账本匹配结果作为统计，不能直接当作真实世界的准确率、
  误报率或漏报率。

## 3. 产品流程

将变化发现分为**确定性通道**和**自主调查通道**，避免把简单结构化差异交给 LLM 兜圈：

- **确定性通道**：模型目录快照对比（`/v1/models` 新增或下线）及已有额度接口的结构化差异，直接生成对比结果或草稿。
- **自主调查通道**：公告、活动规则、定价、使用限制等非结构化政策变化，进入 Agent 自主调查循环。

```text
定时检查 / 人工触发
    ├── 确定性通道（模型目录 / 额度接口）──────────────┐
    └── 非结构化政策变化（公告 / 定价 / 活动页）         │
            ↓                                          │
        建立调查问题 → 搜集证据 → 判断缺口              │
                           ↺ 选择下一步继续调查        │
            ↓                                          │
        充分 / 冲突 / 无法访问 / 预算耗尽              │
            ↓                                          ↓
        按同一政策对比旧值和新值，评估影响 ←───────────┘
            ↓
        小变化留痕 / 生成待审核草稿 / 待核实
            ↓
        人工确认 → 生成账本变更提案（PR / 补丁）→ Git 合并校验 → 人工批准发布
```

### 3.1 调查充分性的判断

每次调查围绕明确的问题，例如某厂家某模型的新用户免费额度是否变化。Agent
检查适用于该问题的事实：政策内容与单位、厂家和模型、用户类型与地区、
生效或截止日期、领取及限制条件、来源权威性、原文证据，以及与旧记录是否
描述同一政策。某些事实对特定政策确实不适用时，须记录“不适用”和依据。

- 关键事实齐全且无未解决冲突：结束调查，生成对比结果。
- 事实缺失：提出缺口并选择相关的下一来源或复查动作。
- 来源矛盾：记录双方和时间，继续查更直接、更新的官方资料；仍无法消解则
  标记冲突。
- 无法访问、预算耗尽或没有合规的后续来源：保留证据和缺口，标记待核实，
  安排重试或人工处理。

原文片段匹配只能证明“片段存在”，不能单独证明模型解读、适用范围或数值
换算正确。模型自报的置信度仅供排序，不能代替字段校验、来源核查和人工确认。

### 3.2 影响分级

| 级别 | 例子 | 处理 |
|---|---|---|
| 小 | 排版或文字变化，政策含义不变 | 自动留痕，不写账本 |
| 中 | 新优惠、额度增加、领取方式变化 | 生成待审核草稿 |
| 高 | 涨价、额度下降、使用条件收紧、模型或活动下线 | 优先提醒并生成草稿 |
| 待核实 | 关键条件缺失、证据冲突或来源不可访问 | 保留缺口，复查或交人工调查 |

影响由业务语义决定，不只看数值变化百分比。生效日期、覆盖用户、区域和模型
范围变化也可能是高影响。上述是首版规则，具体阈值通过试运行结果调整；
无论级别，正式账本和发布均须人工确认。

## 4. 技术架构

首版沿用单机部署、Python 和中心服务现有基础，不引入独立 Agent 框架或新中间件。
每日 systemd timer 和后台手动触发仍使用现有入口；在采集器中增加可恢复的调查
执行器，复用现有规则抽取与 LLM 网关。调查状态、证据和审核记录持久化后，
后台读取并展示。

### 4.1 数据与职责

| 数据 | 建议位置 / 所属方 | 作用 |
|---|---|---|
| 已确认政策 | Facet `ledger/vendors`、`ledger/activities`、`changelog.jsonl` | 唯一正式比较基线 |
| 来源登记 | Facet `ledger/sources.json`，必要的额外采集限制由中心侧配置 | 标识厂家和可信来源；不随意扩充现有严格 schema |
| 原始证据 | `facet-center` 的采集数据目录 | 页面快照、引用、抓取时间、来源 URL 和内容哈希 |
| 调查与草稿 | 中心 SQLite 新增调查、草稿和审核事件记录 | 持久化状态、证据引用、预算、决策和审核历史 |
| 发布产物 | Facet 账本渲染后的 `registry.json` / `intel.json` 及签名 | 仅由人工确认后的账本生成 |

采集进程和中心服务分属不同进程，数据库连接各自创建，沿用 SQLite WAL；
新增表采用向后兼容的迁移，并在部署前备份数据库及证据目录。快照只存公开页面，
不保存授权头、密钥、代理凭据或账户响应；日志和后台展示同样脱敏。

### 4.2 调查状态机

首版针对约 20+ 家厂家、每日定时运行的规模，状态保持精简，使用 4 个核心状态持久化（所有终止原因一并落库）：

```text
investigating → draft_ready   （证据充分且有业务变化，生成审核草稿）
             ↘ needs_review   （证据缺失/冲突、受限/预算耗尽，含 next_retry_at 供下次定时复查）
             ↘ no_change      （证据充分且确认无业务变化）
```

- `draft_ready` 仅表示调查已完成并生成草稿，**不等于事实已人工确认**。
- `needs_review` 涵盖证据冲突、受限（403/JS 渲染/登录墙）、预算耗尽及网络重试；通过 `next_retry_at` 由后续定时任务接管复查，认证限制或禁止抓取不无限重试。
- `no_change` 仅用于证据足以判断没有业务变化；抓取失败不能进入此状态。

进程异常退出时，恢复未完成的 `investigating` 任务及已消耗预算，不重复创建草稿，也不把中断当成成功。

### 4.3 Agent 决策循环

```text
读取调查、账本基线和已取得的证据
while 未终止:
    校验事实、来源和字段级引用，列出缺口或冲突
    if 满足充分性条件: 生成对比并结束
    if 无合规下一步或预算耗尽: 标记待核实并结束
    选择下一动作，先记录原因和预算占用
    执行受限工具，持久化结果和下一步决策
```

首版受限动作：读取已登记来源、读取已保存快照和账本、抓取允许的公开页面、
提取结构化事实、检查引用、比较政策。可跟进的链接必须满足来源策略，不能让
网页或模型自由指定内网地址、任意文件、命令或请求头。

前提约束：仅靠各家文档首页往往无法覆盖完整政策，且部分厂家页存在 JS 动态渲染
或地区屏蔽。因此必须先在来源清单补齐各家的真实公告/定价/活动子页面并配通
`CENTER_PROXY`；遇到纯 JS 渲染且无可用文本的页面，首版直接标记“覆盖不足”进入
`needs_review`，后续按需再评估只读无头浏览器渲染，避免 Agent 在空页面上空转。

来源优先使用厂家直接发布的公告、规则和定价资料；其他来源只作为发现线索或
补充。多源必须检查是否独立，转载同一公告不算独立印证。官方单一来源不自动
等同于错误，但关键事实缺失或冲突时不能判为证据充分。文本引用需能定位到保存的
原文；截图或 OCR 无法可靠核对的内容进入人工审核。

### 4.4 事实、对比与草稿契约

调查层使用独立于正式账本的结构，至少包含：

- 调查 ID、厂家、政策对象、调查问题、状态及时间。
- 基线记录 ID 和内容哈希；字段路径、旧值和旧值来源。
- 发现事实：字段、值、单位、适用范围、有效期、证据 ID 和原文定位。
- 字段状态：`known`、`unknown`、`not_applicable`、`conflict`；
  `unknown` 不映射成零、空字符串或正式账本中可能表示“长期有效”的 `null`。
- 待解决问题、调查动作与原因、终止原因、预算消耗。
- 草稿级别、建议变化、审核结果、审核时间与原因。

比较时先匹配厂家、政策类型、模型、用户群、地区和时间窗口，再比较对应字段。
匹配不确定时不得合并或覆盖。币种、token、请求次数和有效期要保留单位和条件，
不得将货币按估算比例转换成“真实 token 额度”。无法映射到当前账本 schema 的
事实保留在草稿中，交由人工决定是否先演进 schema。

同一疑似变化使用稳定的业务标识及基线版本去重；重复运行更新证据与最后发现
时间，不重复产生待审草稿。不同条件、额度或时间窗口不得仅因标题相似而合并。
人工拒绝须记录原因；若后续关键事实或证据发生变化，可重新进入审核。

### 4.5 预算、调度与失败

- 保留现有每日 `CENTER_LLM_DAILY_BUDGET`，并为单次调查增加请求数、模型
  调用数和总耗时上限；具体默认值在试运行时确定并记录。
- 所有实际发起的模型调用，包括失败和超时，均计入预算；并发下通过事务预占，
  防止重启或竞争使上限失效。
- 一次定时或手动运行内，厂家失败不得阻断其他厂家；进程级互斥防止重叠运行。
- 分别报告成功、部分成功、失败、跳过及原因；系统级失败返回非零退出状态。
  到底哪些部分失败以及是否需要重试，必须在日报和后台可见。
- 常规每日调度保留；高风险待核实事项可设置复查时间。不得把重试计为新发现。

### 4.6 审核、录入和发布

在中心后台增加政策调查列表及详情：旧值/新值、影响级别、适用范围、来源引用、
调查步骤、缺口、预算与结果。支持确认、拒绝及填写原因；补充证据后重新调查。
所有操作使用现有管理员鉴权，记录审核事件。高优先级先在后台突出显示；外部通知
渠道属于后续配置，不视为现有能力。

现有投稿队列可以借鉴，但其当前 `resolve` 只改变队列状态，不能直接视为完成
账本更新。建议新调查和草稿使用专用记录，避免和投稿队列形成两份不一致状态。

人工确认后，需要打通服务器后台到 `hsliuping/Facet` 账本仓库的最后一公里，
避免“后台点确认后还要本地手工抄录”。具体采用**账本变更提案**方式：

- 中心服务根据已确认草稿和基线哈希，生成标准化的账本更新补丁（或对应的
  `record.py` / JSON 变更内容），通过有限权限 Token 自动向 `hsliuping/Facet`
  发起 PR（或导出可一键应用的补丁包）。
- 合并前由 Facet 仓库的 [`validate.py`](../tools/ledger/validate.py) 校验完整
  schema 与跨文件引用，并检查基线哈希是否已漂移；若基线已变化或校验失败，
  拒绝合并并退回重新生成草稿。
- 人工合并 PR 后，再独立批准执行渲染、签名与发布。当前 GitHub Release 自动
  签名与 `pull.py` 拉取链路尚需部署核实，不将其视为已自动打通。

### 4.7 抓取安全与可运维性

- 限制请求方案、允许的域名与重定向；解析和连接时阻止本地、内网及保留地址，
  防止 Agent 被页面诱导访问内部服务。代理配置不得绕过相同策略。
- 遵守目标站点的访问规则和速率限制；403、验证码或登录墙记录为受限，不尝试
  绕过。需要浏览器渲染的站点先标记覆盖不足，浏览器能力另行评估。
- 所有网页、搜索结果和模型输出均是不可信输入；模型只能从受限工具中选择动作，
  不得执行页面指令、调用任意 shell 或修改账本。
- 页面快照、调查事件和审核结果需要备份、容量监控与保留策略；避免在公开仓库
  提交包含凭据或不宜公开的原始内容。具体保留期限部署前确定。

## 5. 分阶段实施

| 阶段 | 主要改动 | 完成标志 |
|---|---|---|
| 0. 修复基础与补齐来源 | 修正快照数据源和目录；明确厂家级失败、部分成功和退出状态；修复历史规则跳过与分流落盘；配通 `CENTER_PROXY` 并补齐试点厂家的真实公告/定价子页面 | 真实来源可生成可读取的快照与正文；失败不再显示全绿 |
| 1. 调查闭环 | 落地 4 状态调查模型、事实与证据契约、确定性 Diff 与受限 Agent 循环、预算和恢复机制 | 模型目录变化走确定性 Diff；非结构化政策缺字段时能自主追查并给出可追溯结果 |
| 2. 对比与审核 | 实现基线匹配、影响分级、去重、后台草稿和人工决定 | 审核者可看到旧值、新值、证据、缺口与全过程；不修改账本 |
| 3. 提案录入与发布 | 后台确认后自动生成 Facet 账本变更 PR/补丁、基线冲突检查、账本校验和人工发布 | 确认草稿无需手工抄录即可进入 Git 审核；校验失败不影响正式账本和线上产物 |
| 4. 小范围试运行 | 使用 `pilot.py` 选择 2~5 家厂家并写入隔离目录，建立人工标注样本和指标 | 达到约定的发现效果和审核负担后，再逐步扩大覆盖 |

阶段顺序是依赖关系，不以自测全部通过替代真实厂家样本验证。

当前实施记录：

- 2026-11-28：`facet-center` 已统一读取 `probe_endpoints`、按厂家合并多个
  模型端点并写入 `data/collect/snapshots`；支持缺少 key 的显式跳过。
- 2026-11-28：页面抓取支持同一厂家多个登记来源、独立元数据和明确结果状态；
  历史规则候选不再永久阻断新一轮 Agent 解读。
- 2026-11-28：Agent 引用验证与分流状态可持久化，日报与管理后台显示
  `success / partial / failed / skipped`，全部失败将返回非零退出状态。
- 2026-11-28：新增 `investigate` 阶段，调查状态和人工审核记录保存到中心
  SQLite；模型目录与额度记录走确定性 Diff，政策候选在预算和轮次限制内补证。
- 2026-11-28：管理后台新增政策调查页，展示旧值/新值、影响、证据、缺口、

## 6. 验收与测试

优先使用本地固定页面、模拟 HTTP/LLM 和临时账本，禁止测试向真实厂家发请求或
改写生产数据。至少覆盖：

1. **自主调查**：首个页面缺少适用范围时继续查；字段齐全后停止；
   来源冲突时不生成“已确定”的结论；预算耗尽后进入待核实。
2. **事实正确性**：新旧政策用户范围不同不直接比较；单位不一致需明确换算；
   未知不等于零或无限期；伪造引用、无证据和截图无法核实时不能判为已验证。
3. **变化发现**：新增优惠、额度下降、涨价、模型下线、条件收紧、纯文案修改
   各有预期结果；单次 404、403 或网络失败不能判定政策下线。
4. **持久化与安全**：中断恢复、并发预算、重复运行去重、拒绝原因、基线变更
   冲突；禁止内网 URL、非法重定向和网页注入的工具指令。
5. **审核与发布**：Agent 无法写正式账本；未确认不得进入发布；基线不一致、
   账本校验或签名失败时不覆盖线上产物。
6. **观测**：所有页面失败时日报和后台不能显示成功；部分成功、跳过和失败
   数量及原因可查，任务异常有明确退出状态。

试运行时单独建立经人工标注的政策变化样本，统计发现率、误报、证据完整率、
从官方发布到发现的时间和每周人工审核量；记录抽样范围及漏掉的来源。当前账本
只覆盖已录入政策，不能把“账本没匹配到”直接视为误报，也不能仅凭它估算真实
世界漏报率。

试运行命令示例（先补齐试点来源并自行选择厂家）：

```bash
CENTER_PILOT_CONFIRM=1 python tools/collect/pilot.py \
  --vendors modelscope,openrouter,siliconflow \
  --root /tmp/facet-pilot-20261128 \
  --ledger /path/to/Facet/ledger
```

试运行数据不得写入生产 `data/collect`；未设置确认变量时只拒绝运行，不发真实
网络请求。报告 `pilot-report.json` 用于人工标注，不作为正式账本或发布输入。

### 采集运行配置界面

采集运行参数在中心管理后台新增「采集配置」页配置，不必直接改 systemd 环境
文件。支持试点厂家、代理、厂家 Key、额度端点、LLM 端点/Key/模型/预算、
新闻接口和预算、调查轮次/时长、抓取间隔及 robots 策略。

配置由后台保存到采集目录 `data/collect/config.json`；POSIX 部署下文件权限为
`0600`，下一次采集进程启动时动态读取。`GET` 接口只返回敏感字段的“已配置”
状态，不回显 Key。页面输入留空表示保持现值，显式点击“清空”才删除。配置文件
优先于普通环境变量；试点 CLI 的 `CENTER_PILOT_VENDORS` 临时覆盖除外。

首次配置完成后，可在「采集状态」页手动运行；线上需先部署新代码，现有
`facet-center` 进程不会自动获得这项后台页面。

## 7. 实施前需确认的运营参数

以下不改变“人工确认后才入账和发布”的边界，可在试运行前确定：

- 首批试点厂家及每家应覆盖的公告、定价、优惠和模型目录页面。
- 单次调查及每日的请求、模型调用、耗时和成本上限。
- 重大变化的通知方式、重试频率、证据保存期限和负责人。
- 哪些政策字段需要扩展正式账本 schema，以及对已有客户端的兼容方案。
